# Спецификация и план реализации: Универсальная система индексации планов (JSON) и динамического дашборда

> **Расположение:** `lift-sdlc/docs/delivery-dashboard/plan.md`  
> **Статус:** Утверждено к исполнению в изолированном субагенте  
> **Цель:** Универсальная система машиночитаемого представления планов (JSON) и интерактивного дашборда для всех текущих (`trade-robot-alpha`, `lift-fixed-price`) и будущих проектов.

---

## 1. Концепция и 4-уровневая иерархия планов

Текстовые планы в формате Markdown (`docs/plans/*.md`, `docs/TODO/*.md`) сохраняются как **первоисточник истины (SSOT)**. Машиночитаемый JSON формируется как актуализированная проекция.

Система связывает между собой 4 уровня артефактов:
1. **Уровень 0: Предварительные / Стратегические планы (`docs/plans/*.md`, `docs/webapp-concept/mvp/05-*.md`):**
   - Макро-цели, инварианты, архитектурные слои, CPM-волны.
2. **Уровень 1: Исполнительные планы агентов (`plan-sdlc`):**
   - Задачи с точными полями `Complexity`, `Risk`, `Depends on`, `Files`, `Acceptance criteria`.
   - В заголовке поле `**Source:**` явно ссылается на Уровень 0.
3. **Уровень 2: Фактическое исполнение агентами (`.sdlc/execution/execute-*.json`, `task-*.md`):**
   - Поле `planPath` указывает на файл плана Уровня 0/1.
   - Поле `planHash` фиксирует SHA-256 хэш плана на момент запуска.
   - Поле `waves[].tasks[]` содержит фактические статусы выполнения (`completed`, `failed`), время и реальный `filesChanged`.
4. **Уровень 3: Заметки и отложенные работы (`docs/TODO/*.md`):**
   - Поля `Blocks:` и `Related:` связывают отложенную задачу с волной или планом.
   - Статусы: `open`, `in-progress`, `blocked`, `promoted`, `done`, `wont-do`.

## 2. Форматы планов и алгоритмы извлечения (Parsing Rules)

Парсер `scripts/lib/plan-indexer/markdown-parser.js` извлекает данные без использования токенов LLM (детерминированно), поддерживая 4 основных стиля:

### 2.1. Заголовок документа (Document Header)
* Заголовок H1: `^#\s+(.+)$`
* Мета-поля:
  - `**Goal:**\s*(.+)`
  - `**Architecture:**\s*(.+)`
  - `**Source:**\s*(.+)`
  - `**Verification:**\s*(.+)`
  - `**Version:**\s*(.+)` или `> \*\*Plan version:\*\*\s*([^\s,]+)`

### 2.2. Задачи: Синтаксические паттерны
1. **Стандартный `plan-sdlc`:**
   - Шаблон: `^###\s+Task\s+([A-Za-z0-9_.-]+):\s*(.+)$`
   - Метаданные:
     - `\*\*Complexity:\*\*\s*(Trivial|Standard|Complex)`
     - `\*\*Risk:\*\*\s*(Low|Medium|High)`
     - `\*\*Depends on:\*\*\s*(.+)` (разбивается по запятым, "none" $\to$ `[]`)
     - `\*\*Files:\*\*` со строками `- (?:Create|Modify|Test):\s*`
     - `\*\*Acceptance criteria:\*\*` со строками `- \[([ xX])\]\s*(.+)`
2. **Волновой формат `trade-robot-alpha`:**
   - Шаблон: `^####\s+Task\s+([A-Za-z0-9_.-]+):\s*(.+)$`
   - Привязка к волнам: поиск предшествующего `^###?\s+(Wave\s+[A-Za-z0-9_.-]+)` или таблицы `SHIPMENT SCOPE`.
3. **Review-Fix формат `lift-fixed-price`:**
   - Шаблон: `^###\s+([XW][0-9]+)\s+[—-]\s*(.+)$`
   - Метаданные:
     - `\*\*Severity:\*\*\s*([A-Za-z]+)`
     - `\*\*Batch:\*\*\s*([A-Za-z0-9_-]+)`
     - `\*\*Files to modify\*\*`
4. **Заметки `docs/TODO/*.md`:**
   - Извлечение таблицы метаданных:
     - `\|\s*Status\s*\|\s*([^|]+)\|`
     - `\|\s*Priority\s*\|\s*([^|]+)\|`
     - `\|\s*Blocks\s*\|\s*([^|]+)\|`
     - `\|\s*Related\s*\|\s*([^|]+)\|`
   - Или фронтматтер-строки: `\*\*Status:\*\*\s*(.+)`, `\*\*Trigger:\*\*\s*(.+)`.

### 2.3. Сохранение Markdown-фрагмента задачи (Chunking)
Для каждой задачи парсер сохраняет точный диапазон строк исходного файла (`markdownSource`), что позволяет дашборду отображать богатые детали без повторных обращений к диску.

## 3. Модуль сверки статусов (Reconciler Engine)

Модуль `scripts/lib/plan-indexer/reconciler.js` вычисляет итоговый статус задачи:
1. Если задача присутствует в `.sdlc/execution/execute-*.json` со статусом `completed` $\to$ статус `done`.
2. Если в markdown все чекбоксы `- [x]` отмечены и/или есть коммит в Git $\to$ статус `done`.
3. Если задача помечена как заблокированная или связана с `TODO` со статусом `blocked`/`P0` $\to$ статус `blocked`.
4. Если есть промежуточные изменения файлов или коммиты WIP $\to$ статус `in_progress`.
5. Иначе $\to$ статус `todo`.

Статус самого плана:
* Если путь содержит `/archived/` $\to$ `archived`.
* Если все задачи `done` $\to$ `done`.
* Если есть задачи `done` или `in_progress` $\to$ `in_progress`.
* Иначе $\to$ `proposed`.

## 4. Архитектура дашборда: Вариант Б с переходом к Варианту А

### Вариант Б (Стартовый):
* Автономный файл `delivery_dashboard.html`;
* Встроенный JSON `<script id="delivery-data" type="application/json">`;
* Чистый Vanilla JS + CSS (без внешних CDN, открывается через `file://`);
* Модульная архитектура UI:
  - `DAG Flow` (SVG-кривые связей, подсветка upstream/downstream);
  - `Task Matrix` (сортируемая таблица задач);
  - `TODOs & Blockers` (матрица блокеров);
  - `Raw JSON` (просмотрщик с кнопкой копирования);
  - `Task Inspector Drawer` (выезжающая панель с чек-листом, файлами и Markdown).

### Переход к Варианту А (Будущий Vite + React SPA):
* Модель данных `delivery-model.js` уже написана как чистый ESM;
* React-компоненты просто заменяют рендеринг DOM, потребляя тот же `DeliveryGraph` через `fetch('/api/delivery-graph')`.

## 7. Резолюция экспертных ревью (UX / PM / Architecture) и внедренные улучшения

По итогам параллельного аудита изолированными агентами внедрены следующие решения:

### 7.1. Архитектурные исправления (System Architecture)
- **Устранение «парадокса мутации planHash»:** Хэш SHA-256 файла Markdown меняется при простановке чекбоксов `- [x]`. Связывание запусков с планами переведено на 3-уровневый матчер (нормализованный путь `planPath` $\to$ хэш $\to$ базовое имя), а `planHash` сохранен как штамп аттестации с вычислением `driftStatus: "pristine" | "drifted"`.
- **Безопасность идентификаторов в DOM:** Имена задач вида `Task 0.1` преобразуются в slug (`node-task-0-1`), исключая синтаксические ошибки в CSS-селекторах `querySelector`.
- **Устойчивый лексер с защитой блоков кода:** Блоки кода (```` ``` ```` и `~~~`) изолируются до парсинга задач, что предотвращает ложные срабатывания на комментариях `# Task ...`. Поддержаны разделители-миддоты (`·`), списочные задачи `* **Task N**` и примечания в скобках.
- **Чистая headless-модель (`model.js`):** Класс `DeliveryGraphModel` полностью изолирован от DOM и реализует алгоритмы графа (топологическая сортировка, критический путь, вычисление готовых к запуску задач).

### 7.2. UX/UI улучшения (UX Design)
- **Немодальный Drawer:** Оверлей сделан прозрачным (`pointer-events: none`), что позволяет взаимодействовать с графом и видеть подсвеченные связи при открытой панели задачи.
- **Направленные стрелки на SVG-кривых:** Добавлены маркеры `<marker id="arrow-upstream">` и `<marker id="arrow-downstream">` для наглядной визуализации направления зависимостей.
- **Уведомления Toast вместо `alert()`:** Системные блокирующие окна заменены на плавные всплывающие тосты с автоскрытием.
- **Расширенный поиск:** Полнотекстовая фильтрация теперь проверяет не только заголовки, но и пути файлов (`create`, `modify`, `delete`, `test`).

### 7.3. Управление поставкой и метрики (Product Management)
- **Вычисление критического пути (Critical Path / CPM):** Модель вычисляет максимальную цепочку невыполненных зависимостей (`getCriticalPath`).
- **Фильтр «Ready to Execute»:** Выделение задач, у которых все upstream-зависимости выполнены и отсутствуют блокирующие P0 TODO.
- **Действие «Copy Agent Prompt»:** Быстрое копирование команды запуска агента (`/execute-plan-sdlc --task <id>`) прямо из инспектора задачи.
- **Коррекция KPI:** Метрика «Delivery Velocity» переименована в точную «Scope Completion».
